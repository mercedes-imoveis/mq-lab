**Update (22/11, after G):** the workflow now implements design A' and the factory design (repo variable `MODE`: `AP` = job-level concurrency on `heavy` with a fixed group and `cancel-in-progress: true` on merge_group, no workflow-level concurrency; anything else = no limit). `gate` has `needs: heavy`, `if: always()` and succeeds only when `heavy == success`. Ruleset `main-mq` is disabled again, `MODE` deleted, open bench PRs closed.

## Answers (spec section 13, questions 1 to 5)

1. **Does `min_entries_to_merge` hold the build dispatch? No.** D2 and D2b: the first merge_group run was created 19 s after the first enqueue. The minimum only holds the merge into main: D2b (2 PRs, min 4, wait 5) had the head build green at about 2m30s and merged at 5m35s after the first enqueue. With the minimum met (D2, 4th PR at 90 s) the merge came right after the head build.
2. **Does `max_entries_to_build: 1` turn batching off? Yes.** D1a: 4 PRs at once gave 4 complete builds, one per entry, 398 s of runner, 9m18s to the last merge, each PR merged alone and main tip = the last tested SHA. D1b (build 10): 1 complete + 3 cancelled, 102 s of runner, 2m34s, all 4 merged together.
3. **Design A or B (6 PRs, 1 per 60 s, build 90 s)?** A: 1 complete + 5 cancelled (cancelled after 45 to 80 s), 404 s of runner, about 16 billed min, all 6 merged together at 7m55s (average wait per PR 5m21s). B: 5 complete + 1 cancelled, 550 s, about 18 billed min, 5 merges, first PR in main at 2m19s (average per PR 3m02s). A is cheaper (about 12% less in billed minutes, 27% less in runner seconds) and slower per PR when arrivals are spaced at about the build length; B is cheaper only when arrivals are denser than the build (not measured here).
4. **GITHUB_TOKEN enqueue:** not tested here (robot task, T3).
5. **Does merge_group read `actions/cache` saved by a `push` on main? Yes**, through `restore-keys`. The push run saved `lab-cache-<main sha>`; merge_group (and pull_request) runs logged "Cache restored from key: lab-cache-<main sha>" (`cache-hit` is false because only the prefix matched, which is the expected value for restore-keys). Examples: run 45033333409 and 45035090744 (see the "report cache" step).

D4 (main tip = tested SHA): yes in every green round. Each PR's squash commit SHA equals the head_sha of one merge_group run, and the main tip after the round equals the head build's SHA (D1a: 4 PRs, 4 SHAs matched; D1b 26fb00bb; D2 ccdae6f2; D2b 88d84923; D3a d8acc8a0; D3b 725b14cf).

## Findings that change the plan

- **A cancelled run can leave no check at all.** When the workflow-level cancel hits a run before its jobs start (0 s runs in F: `bdd3538f`, `d0720b36`), the entry has no `gate` check and stays `AWAITING_CHECKS`. If the head build then fails, the cascade stalls: F stalled 14 min (until I changed the ruleset timeout from 60 to 5 at 15:28, then moved 2 min later), G stalled 19 min (moved 3.5 min after I rewrote the ruleset at 16:01; stalled again at 16:07 for 7+ min until I stopped). A timeout of 5 or 6 min did not remove the entries by itself; only a ruleset write seemed to wake the queue (2 cases, not proven as the cause).
- **Removal order is not "culprit last".** F: removals in the order #39, #40, #41 (culprit), #42; the innocent #42 was removed last because its rebuild still contained #41's file. With build 10 the "last removed = suspect" rule of the spec would blame #42. In G, #43 went first. The robot cannot pick the suspect by position; it has to read the failed run (which files/commits are in the group) or use the cap of 1 requeue per SHA.
- **Final state of F:** main has 0 `FAIL*` files (red proof) and none of the 4 PRs entered; the queue took 26 min and 10 merge_group runs (4 failed, 6 cancelled) to empty.
- **Cancelled runs are not free:** a run cancelled 3 s after the start still bills 1 min per started job (D1b run with 3 s: 2 jobs = 2 billed min in my estimate).
- **gh pr merge:** with `allow_auto_merge` false, `gh pr merge N --squash` and `--auto` both fail: "GraphQL: Auto merge is not allowed for this repository (enablePullRequestAutoMerge)". With it true, `gh pr merge N --squash` on a green PR enqueues it (the CLI prints "The merge strategy for main is set by the merge queue" and the PR shows as QUEUED); `--auto` on a PR with checks still pending sets `autoMergeRequest`, and the PR entered the queue by itself about 1 min later when its check went green (E4, #50: auto set 16:17:38, queued 16:19:31, merged 16:22:18). `--auto` on an already green PR also enqueues at once (#48).
- Actions are pinned by SHA (org policy): `actions/checkout` v4.2.2, `actions/cache/save` and `restore` v4.2.4.

## Design A' (job-level concurrency + gate that always reports): results (22/11, BRT afternoon)

Doc (docs.github.com, "Control the concurrency of workflows and jobs"): "This means that there can be at most one running job or workflow in a concurrency group at any time. ... By default, any existing `pending` job or workflow in the same concurrency group will be canceled and the new queued job or workflow will take its place. To also cancel any currently running job or workflow in the same concurrency group, specify `cancel-in-progress: true`."

Setup: no workflow-level `concurrency`; `heavy` has `concurrency: {group: mq-heavy, cancel-in-progress: true}` on merge_group; `gate` (`needs: heavy`, `if: always()`) fails unless heavy succeeded. HEADGREEN, build 10, min 1, merge max 10, check timeout 20 min, 5 PRs per round, 1 enqueue / 30 s via `enqueuePullRequest`. "Billed min" = my estimate (ceil per job, cancelled jobs included).

Findings:

1. **No stall.** Every merge_group run reported `gate` (cancelled `heavy` gives gate=failure after about 3 s), so no entry stayed `AWAITING_CHECKS` for lack of a check (F and G did). The queue emptied in 16m31s (A'2) and 11m34s (A'3) with no ruleset write.
2. **But innocents are ejected.** A cancelled entry's `gate` is a failure, so the entry is `UNMERGEABLE`. When the head build fails, the queue removes entries from the front (`failed_checks`), one rebuild per removal: A'2 removed #56, #57 (innocent), then #58 (culprit); A'3 removed #61, #62, then #63 (culprit). Only the 2 entries behind the culprit merged. Timelines (REMOVED_FROM_MERGE_QUEUE_EVENT, reason `failed_checks` in all 6 removals): A'2 #56 removed 16:48:01, #57 16:55:13, #58 16:57:30, #59 and #60 merged 16:59:49; A'3 #61 17:07:35, #62 17:09:53, #63 17:12:06, #64 and #65 merged 17:14:19.
3. **Race on simultaneous rebuilds.** In A'2, after the removal of #56 four runs started within 3 s (16:48:05-16:48:08). The running `heavy` of the first one (3cac34a2) was not cancelled by the newer jobs: it ran until 16:53:07 (300 s) and the head's `heavy` stayed pending until then (04f25a44 started 16:53:09). Cost: about 5 min of extra wait and 300 s of runner. Not seen in A'3.
4. **Green path works.** A'1: 5 PRs 30 s apart, 1 complete + 4 cancelled builds, 235 s of runner, all 5 in main together 4m23s after the first enqueue (5 gates reported, none `AWAITING_CHECKS`; 4 were `UNMERGEABLE` until the head went green, and the queue still merged all 5).
5. **Factory (ALLGREEN, no cancel) on the same failure (3rd of 5):** 7 builds (4 success, 3 failed), 686 s, 21 billed min, 5m28s to empty, only the culprit #68 removed, #66, #67, #69, #70 merged (#66 and #67 alone, #69 and #70 together). Fewer builds, a fraction of the waiting and no innocent ejection in the failing case. A'2/A'3 cost 36 and 32 billed min (+52% to +71% vs the factory) and took 2x to 3x longer.

Conclusion: A' does not stall the queue (the F/G deadlock is gone), but with one bad PR it is worse than the factory design on every axis measured (time to empty 11-17 min vs 5.5 min, 32-36 vs 21 billed min, 2 of 4 innocents ejected vs 0). On green runs A' is cheaper in runner time (A'1: 235 s for 5 PRs; the factory green case was measured only with 4 PRs in round A: 379 s, 2m28s, not the same N). Recommendation for production: keep the factory design (no cancel, ALLGREEN, `gate` as the required check) and save cost with path filters, cache and a smaller `max_entries_to_build` rather than cancelling queue builds. If cancel is ever required, A' is the only variant of those tested that does not deadlock, but the `gate` of a cancelled build must not fail innocents (untested idea: report success only for a superseded entry, which would green-light code that was not built, so it needs the owner's decision).

## Requeue robot (T3, 22/11 afternoon, design A' with the robot)

Files: `.github/workflows/mq-requeue.yml`, `scripts/mergeQueue/{requeue,ledger,sweep}.mjs`. `requeue.mjs` and `ledger.mjs` are copies of `scripts/ops/mergeQueue/` from landing-pages (branch `ci/tiered-pr-fast-post-merge-heavy`, the corrected rule: everybody removed for `failed_checks` goes back once per head SHA; removed again with the same SHA = suspect; stuck queue = alert). `sweep.mjs` is the I/O side (reads PRs, timeline, runs; calls `decide()`; enqueues with `expectedHeadOid`, never `jump`; one hidden ledger comment per PR; the suspect comment carries a marker so it is posted once). Triggers: `pull_request_target` (`dequeued`, `closed`), `workflow_run` of `ci`, `workflow_dispatch`; runs from the default branch, no PR code checked out; concurrency `mq-requeue`, no cancel.

### Answers

1. **Can the `GITHUB_TOKEN` enqueue (`enqueuePullRequest`)?** With `permissions: pull-requests: write` alone: **no**, `gh: Resource not accessible by integration` (runs 45050888619, 45050862198). With `contents: write` + `pull-requests: write`: **yes**, the PRs entered the queue with `github-actions[bot]` as enqueuer (#71-#73, 17:42:47-17:42:51 UTC, run 45050965346).
2. **Does the resulting `merge_group` start the workflow? No.** The merge-group branches were created (`gh-readonly-queue/main/pr-71-...`), but no `merge_group` run of `ci` appeared in the next 5 minutes (last run 17:39:44, nothing after 17:42:47) and the entries sat in `AWAITING_CHECKS`: the queue is stuck, which is worse than not enqueuing. Doc (docs.github.com/en/actions/concepts/security/github_token, "When GITHUB_TOKEN triggers workflow runs"): "events triggered by the GITHUB_TOKEN will not create a new workflow run, with the following exceptions: workflow_dispatch and repository_dispatch events always create workflow runs." (`merge_group` is not an exception.) The same enqueue by a user token (my own, the bench PRs and, later, the robot with a user token in secret `MQ_ROBOT_TOKEN`) created the `merge_group` run at once.
3. **GitHub App?** Not tested: there is no App credential in the repo secrets (the org Apps `mercedes-imoveis-flux/reader/upgrade/alerts` exist, their keys are not stored here) and I did not create one. What a **user token** proves: a non-`GITHUB_TOKEN` identity makes the queue run. What is still unverified: that an App installation token behaves the same for `merge_group`; the docs say only `GITHUB_TOKEN` events are suppressed. App permissions to request: Pull requests read/write, Contents read/write (needed by the enqueue mutation, shown in answer 1), Actions read (for `gh run view --log-failed`), Metadata read. The landing-pages workflow reads `vars.MQ_ROBOT_APP_CLIENT_ID` and `secrets.MQ_ROBOT_APP_PRIVATE_KEY` (PR branch `orq/mq-requeue-workflow`). For this bench the secret `MQ_ROBOT_TOKEN` held a user token during the rounds below and was **deleted at the end**.

### Findings that changed the robot

- **Requeue everybody together fails.** The group of requeued PRs still contains the culprit, so the head build fails again and the queue removes the front entries first: innocents get the same SHA twice and are accused (R2). The fix in `sweep.mjs`: requeue at most **one** PR per sweep, and none while a PR the robot already put back is still in the queue. A group of one gives an exact verdict. Cost: the requeue phase is serial (one build per removed PR); it only happens after a red group.
- **The sweep also runs on `closed` (merged)**: the merge of the PR in flight frees the slot but emits no later `workflow_run`; without this trigger the next requeue waits for an unrelated event.
- **The first cascade is slow with A'**: R3 took 14 min to remove 3 PRs (a 7-minute gap between two removals, the simultaneous-rebuild race already seen in A'2). That time is the queue's, not the robot's.
- A removal counts only while it is the PR's last queue event (an `AddedToMergeQueueEvent` after it means already requeued); a commit pushed after the removal blocks the requeue.
- `pull_request_target` supports `enqueued`/`dequeued` (docs, "Events that trigger workflows") and runs from the default branch, so the robot never runs PR code with a write token.

Final state: ruleset `main-mq` disabled, variable `MODE` and secret `MQ_ROBOT_TOKEN` deleted, bench PRs closed. The robot workflow stays in place (no secret: it would fall back to nothing and go red, by design).
